# 错误码

`AppError` 的 `code` 是对外契约的一部分：前端按它分流，用户按它判断「该重试、该改配置、还是该换做法」。
所以码值**只增不改**——改一个已有码的语义等于破坏所有依赖它的判断。

承载类型是**数字字符串**（`"1001"`），不是 int：响应信封 `{code, message, data}` 里的 `code` 是 `string`，
与 HTTP 状态码的 int 从类型上分开，前端写 `e.code === "4102"` 就不会有歧义。

- `message` 是给用户看的一句话：不出现字段名、堆栈、上游原文
- `details` 是补充定位信息，可为空，界面上收在错误条的展开里
- `"9999"` 是「这不是 AppError」的兜底码：任何裸 error 走到出口都归到它

段位的归属表在 `AGENTS.md §2.4`；新增码时按域挑段位，不跨段复用。

## 前端已落地的码级分流

| 码 | 前端动作 |
|---|---|
| 4102 | 摘掉那张失效的审批卡，并说明「这条已经处理过了」 |
| 3101 / 3111 / 3113 / 3114 | 错误条上给「去设置」按钮——重试解决不了的配置问题，不给入口就是让用户干瞪眼 |

环境类问题（`9704` / `9709` / `9711`）不走码分流：前端在 `bootstrap` 里读环境闸门，
`ready=false` 就整屏进向导，轮不到这些码露面。它们出现在错误条里只有一种情况——
闸门判定之后环境又坏了（Node 被删、PI 被卸载），此时按通用错误条显示。

其余码走通用错误条：显示 `message`，需要时展开 `details`。

## 一个码承载多种语义的情形

同一码下并列多条含义是有意为之，前提是**用户的处置动作一致**：

| 码 | 并列的含义 | 为什么合成一个 |
|---|---|---|
| 1005 | 文件不存在 / 读取失败 / 目录不存在 / 背景图被挪走 | 处置都是「去看路径与权限」 |
| 1002 | 工作目录为空 / 请求方法不在白名单 | 前者去顶部选文件夹，后者只可能出在开发期，都不该弹给用户 |
| 1107 | 入参解析失败（各 API 统一）/ 决策动作取值不对 / 思考档位不对 / 技能包不是 base64 | 都是「请求没构造对」，处置都是回到界面重填一遍 |
| 2001 | 配置读写失败 / 装配缺件（配置·仓储·事件出口·运行环境） | 都属「程序没装好」，运行期不该出现，出现了就重启或重装 |
| 7004 | zip 里有不安全路径 / 没有可用的 Python / pip 引导失败 | 处置都是「换一份完整的内置包或走系统 Python」 |
| 9701 | 进程已退出 / 不再接受指令 / 指令没送达 / 确认没送达 | 都是「这一轮断了」，下一条消息会自动重新拉起 |

反之，**处置动作不同就必须分码**：`3103`（连不上或上游拒绝）与 `3114`（没保存 API Key）
分开，是因为一个要查网络与地址、一个只要补密钥。并列含义新增时必须回头核对这一条。

代价：码表会随语义细分继续增长，而「处置动作一致」这个判断是人做的——
判断错了就会表现为「提示与实际原因不匹配」，这类问题只能靠改码归属来修，不能靠改文案掩盖。

## 取舍

- **码是对外契约，段位是内部约定**：前端只认码，不读包结构；内部重排包不会破坏界面判断。
- **不给每个失败点单独开码**：`1005` 之下并列六种读失败。全展开会得到 200 多个码，
  而用户能做的动作只有三四种——码数与动作数不匹配时，多出来的码只是噪音。
- **作废的码不回收复用**：`9101–9105`、`9107` 这类因设计变更而消失的码保留空位，
  不复用给新语义。历史日志与旧包里的含义必须是唯一的。
- **不映射上游错误码**：PI 报的错原样经 `chat:error` 呈现。映射表会随上游漂移，
  且映射后用户看到的不再是上游真正说的那句话。

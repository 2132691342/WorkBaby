# 错误码

`AppError` 的 `code` 是对外契约的一部分：前端按它分流，用户按它判断「该重试、该改配置、还是该换做法」。
因此码值**只增不改**——改一个已有码的语义等于破坏所有依赖它的判断。

码值是**数字字符串**（`"1001"`），不是 int：`{code, message, data}` 里的 `code` 是 `string`，
与 HTTP 状态码的 int 从类型上分开；前端判断写 `e.code === "4102"`。
下表列出的编号就是字符串的内容。

`message` 是给用户看的一句话（不出现字段名、堆栈、上游原文）；`details` 是补充定位信息，可为空。

前端目前已落地的码级分流：`"4102"` 摘掉失效审批卡并说明；`chat:error` 里 31xx 的
配置类错误（`"3101"` / `"3102"` / `"3104"` / `"3111"` / `"3112"` / `"3113"` / `"3114"`）在错误条上
给出「去设置」动作——重试解决不了的配置问题，不给入口就是让用户干瞪眼。

## 一个码承载多种语义的情形

同一码下并列多条含义是有意为之，前提是**用户的处置动作一致**：

- `1005` 同时表示「文件不存在」与「读取失败」——两者都只能让用户去看路径或权限
- `2001` 表示启动装配缺件（配置 / 工具注册表 / 事件出口 / 数据仓储未就绪）——都属于「程序没装好」，不该出现在运行期
- `2304` 覆盖开机自启的全部失败面——处置动作都是「去系统里手工设置」
- `3103` / `3111` 把「服务连不上」与「参数没给」分开，因为它们的前端引导完全不同

反之，**处置动作不同就必须分码**：`1009`（写前必读）与 `1010`（edit 未命中共 3 种：
找不到 / 匹配多次 / 新旧相同）分开，是为了让前端能分别提示「先读一遍」与「内容对不上」。

代价是码表会随语义细分继续增长，且同一码的多种含义依赖「处置动作一致」这个判断——
判断错了就会出现前端提示与实际原因不匹配。新增并列含义时必须回头核对这一条。

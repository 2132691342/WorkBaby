# 01 · 总体架构

## 分层

```
main.go / app.go              桌面壳：Wails 生命周期、单实例、托盘、嵌入前端资源
   │
   ├─ internal/api            组合根 + 系统能力绑定（唯一允许 import wails runtime 的包）
   │     依赖全部 service，装配顺序即依赖顺序
   │
   ├─ internal/server         HTTP 层：gin 路由（/api/v1）、统一响应、SSE Hub
   │     只调 api.Handler 方法，不含业务规则
   │
   │  ── 以下为业务层，互不横向依赖，只向下依赖 ──
   ├─ internal/service        编排层：会话、审批、任务、文件、技能、MCP、知识库、记忆…
   ├─ internal/core           Agent 内核：ReAct 循环、护栏、事件、压缩、上下文
   ├─ internal/tool           工具契约、注册表、内置工具
   ├─ internal/llm            Provider 抽象与三家协议实现
   ├─ internal/capability     能力注册表（上下文装配 / 工具暴露 / run 后沉淀）
   ├─ internal/memory         长期记忆（Markdown + FTS5）
   ├─ internal/rag            知识库分块、索引、检索
   ├─ internal/skill          技能解析与注册表
   ├─ internal/mcp            MCP 子进程客户端与管理
   ├─ internal/runtime        数据目录、内置运行时、工作区沙箱
   ├─ internal/pet            桌宠状态机与窗口
   ├─ internal/event          事件总线与 run 事件日志
   │
   ├─ internal/repo           数据访问（gorm），每个 DO 一个 repo
   ├─ internal/domain         数据对象与状态机常量（无逻辑）
   ├─ internal/bootstrap      App 组合根：repo 实例唯一装配点
   ├─ internal/config         Viper 配置与用户配置文件
   ├─ internal/db             数据库连接、迁移、FTS5
   ├─ internal/pkg            叶子工具库（错误、ID、日志、加密、路径、分词…）
   └─ internal/tray / singleinstance / db
```

## 依赖约束

由 `scripts/check-boundaries.ps1` 强制，违反即失败：

| 约束 | 含义 |
|---|---|
| `pkg-no-internal` | `internal/pkg` 不得依赖任何 internal 包（保持叶子） |
| `domain-no-upward` | `domain` 只定义数据与常量 |
| `repo-no-upward` | `repo` 不得依赖 service / api |
| `api-no-repo` | `api` 不得直接 import repo（必须经 service） |
| `service-no-http` | `service` 不得 import gin / wails（HTTP 概念只在 server 层） |
| `server-no-downward` | 业务层不得反向依赖 server |
| `core-no-upward` / `core-no-http` | 内核不依赖上层，也不感知 HTTP |
| `contract-version-sync` | 后端 `domain.ContractVersion` 与前端 `UI_API_CONTRACT_VERSION` 必须一致 |

## 启动装配

`api.Handler.Startup(ctx)` 是唯一装配入口，顺序即依赖顺序（摘主要步骤）：

1. `runtime.Resolve()` 定位数据根目录（`WORKBABY_HOME` 或 `%APPDATA%\WorkBaby`）
2. 日志初始化（`pkg.Init`）、配置初始化并补齐 `model.json` / `mcp.json` 模板
3. 打开 SQLite（WAL、`busy_timeout`、**连接数固定 1**），执行迁移与 FTS5 建表
4. `bootstrap.New(db)` 一次性构造全部 repo
5. `registry.Build` 用主密钥解密 API Key 后构造各 Provider（未就绪只告警，不阻塞启动）
6. 注册全部工具 → `toolReg.SelfCheckSchema()`（schema 不合法直接启动失败）
7. 记忆、技能（内置 → 全局 → 工作区）、MCP（以 `mcp.json` 为源同步进 DB 并拉起子进程）
8. 构造 `ChatService` 并逐个注入能力（信任、事件日志、检查点、文件、变更、钩子…）
9. `approvalSvc.RearmPending / LoadGrants`、`chatSvc.ReapInterrupted`（跨重启恢复）
10. 构造 `ChatTaskService`（必须在 ChatService 之后：复用其工具注册表与护栏链）
11. 桌宠控制器订阅 `chat:*` 事件；`bindEventBridge()` 把 `app:*` 事件桥到 Wails

`app.go` 随后启动内嵌 HTTP Server（随机端口）并发 `app:ready{server_port}`，前端据此初始化 API 基址。

## 双通道

| 通道 | 承载 | 说明 |
|---|---|---|
| HTTP `/api/v1` + SSE | 全部业务 API 与实时事件 | 浏览器可见、可重放、可用 curl 调试 |
| Wails 绑定 | 系统能力：窗口、托盘、文件对话框、剪贴板 | 只有这些需要操作系统原生能力 |

`app:*` 事件经 `bindEventBridge` 转发到 Wails；`chat:*` 不转发——SSE 已覆盖，避免每条增量一次 IPC 序列化。

## 并发模型

| 场景 | 机制 |
|---|---|
| 会话内串行、跨会话并行 | `ChatService.locks` 会话级互斥锁，关键区只覆盖「占位落库 + run 登记」 |
| 一次 run | 独立 goroutine + `context.WithCancel`，句柄存 `runRegistry`，前端「停止」即取消 |
| 只读工具并行 | `Loop` 内满足「全部只读且数量 > 1」时按 `Config.Parallel`（默认 4）并发，结果按调用顺序回填 |
| 后台任务 | 队列容量 64 + 2 个 worker goroutine，取消走 per-task `CancelFunc` |
| 事件发布 | `event.Bus` 在调用方 goroutine 同步执行；SSE Hub 每个客户端独立 256 缓冲，慢客户端直接断连触发重连 |
| SQLite | `SetMaxOpenConns(1)` + WAL，彻底规避写锁竞争 |
| capability 沉淀 | run 结束后每能力一个 goroutine，各自 30s 超时 |

## 一次对话的完整数据流

```
前端 ChatInput
  │ POST /api/v1/chat/stream {session_id, content, file_ids}
  ▼
server → api.Handler → ChatService.SendStream
  │  ① 会话级锁 → 取会话 → 补齐 Provider/Model
  │  ② prepareRun：分配 runID、登记执行平面、落 user 消息 + assistant 占位（streaming）
  │  ③ 返回 {run_id, assistant_msg_id}，后台 goroutine 继续
  ▼
runLLM（goroutine）
  │  上下文装配：能力 Preload（环境/工作区/记忆/知识/技能）→ BuildSystem 预算裁剪
  │  历史清洗：RebuildHistory 剔除空占位与孤儿 tool 结果
  │  组装 core.Loop：Provider + 工具暴露 + 护栏链 + Sink(事件映射) + Hooks(插话/续跑)
  ▼
core.Loop.Run
  │  for turn：压缩 → 请求模型（流式）→ 有工具调用则执行 → 回填 → 写检查点
  │  事件经 Sink → service 映射为 chat:* → event.Bus → SSE
  ▼
收尾
  │  assistant 落库（正文/思考/工具调用/用量/耗时/停止原因）
  │  发 chat:done（落库后才发，避免前端空内容覆盖）
  │  能力 Capture（记忆沉淀等）→ 目标模式判定是否继续
  ▼
前端 SSE 收到 chat:done → 拉权威快照对账
```

前端同时监听 `GET /api/v1/events?scope=chat&runId=...`，首连即重放该 run 已缓存的事件；缓冲被覆盖时后端发 `chat:gap`，前端转全量回补。

## 目录约定

- 路由：`internal/server/routes_<域>.go`，一个域一个文件，只在 `router.go` 注册
- 处理：`internal/api/api_<域>.go` 只做参数透传，不含业务规则
- 业务：`internal/service/<域>.go`，跨模块的复杂链路单独成文件（如 `chat_runs.go`、`durable_pause`）
- 数据：`internal/domain/<表>.go` 定义 DO 与状态常量；`internal/repo/<表>.go` 提供访问
- 前端：`frontend/src/src` 下 `api / stores / components / chat / composables / i18n / types`

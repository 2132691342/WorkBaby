# 07 · 聊天与会话

## 会话

`ChatSessionDO`：`ProviderID / Model / WorkspacePath / PermissionMode / Kind / ParentID / Pinned / MetadataJSON`。

- 权限四档 `restricted / default / auto_edit / yolo`，会话切换时同步后端
- `Kind = side` 是辅助会话（见下），不出现在侧栏列表
- 目标模式、压缩边界等会话级状态存 `MetadataJSON`
- 会话可绑定本地工作区目录；未绑定时用默认工作区

## 一次发送的完整链路

`ChatService.SendStream(ctx, sessionID, content, fileIDs, params)`：

1. 取会话级锁（关键区只覆盖「占位落库 + run 登记」，跨会话互不阻塞）
2. 补齐 Provider/Model 兜底、解析附件（图片转多模态 part）
3. `prepareRun`：取消该会话遗留的挂起审批 → 分配序号（user + assistant 占位各一条）→ `runID` → 登记执行平面 → 落 user 消息 + assistant 占位（`streaming`）→ 消息计数 +2
4. 建可取消 ctx 并登记到 `runRegistry`，立刻返回 `{run_id, assistant_msg_id}`
5. 后台 goroutine `runLLM` 继续：墙钟上限（Agent 定义或 10 分钟）

`runLLM → executeAgent` 的装配顺序：

```
技能同步 → Agent 模型/推理强度覆盖 → UserPromptSubmit 钩子（可阻断）
→ 取 Provider → 拉历史（含多模态）→ 辅助会话前缀 → 上下文装配（能力 Preload + 预算裁剪）
→ 工具两级过滤（技能白名单 → Agent 策略）→ 预算计算
→ newCoreLoop（Sink=事件映射，Hooks=插话/续跑，注入 Delegator 与 InputRequester）
→ RebuildHistory 清洗后 Run（或 Resume）
```

收尾：按每次上游调用落 `token_usages` → 写运行记录 → assistant 落库（正文/思考/工具调用/停止原因/用量/耗时）→ 失败或取消时回滚本 run 新增的免审授权 → 反幻觉核验（声明改了哪些文件 vs 实际变更记录）→ 能力沉淀 → 目标模式判定是否继续 → **发 `chat:done`（落库后才发）**。

## 消息与流式

消息角色：`user / assistant / tool / system`。`Seq` 会话内单调，工具消息与注入消息统一分配序号，避免撞号。

流式路径：

```
POST /chat/stream → 返回 run_id
GET /events?scope=chat&runId={run_id}  ← SSE
```

`chat:*` 事件由 service 的事件映射器产生（内核事件 → 前端协议），核心有：`stream.start / stream / turn-start / stats / tool / tool-result / approval / done / error / compressed / steer / subagent-*`。

**可靠性三件套**：

- 每条事件带单调 `seq`，`Last-Event-ID` 断线重放
- 重放缓冲被覆盖（或事件过大只记占位）→ 后端发 `chat:gap`，前端转全量回补
- 看门狗：全静默 75s 或只有心跳无业务事件 5 分钟 → 重连；退避 500ms 起 ×2ⁿ，上限 8s

前端对账（`chat/models/merge`）：流式期间本地累积正文，收尾时按 `dedupe / fill / missing` 三种情境与权威快照归位，避免重影、重复堆叠、丢增量。

## 中断与插话

- **停止**：`POST /chat/sessions/:id/cancel` 取消 ctx，内核收到后 `finish(cancelled)` → `chat:done`
- **插话（steer）**：run 进行中可推送新消息，落库后进入队列，在工具执行完的轮间注入（`Hooks.Steering`）
- **续跑（follow-up）**：run 想结束时先问用户钩子是否还有反馈，最多续 3 次

## 审批与暂停恢复

工具策略门判定为 `ask` 时进入 `ApprovalService.Approve`：

1. 落 `approval_records`（`pending`）→ 发 `chat:approval{id, command, reason, risk, can_remember}`
2. 阻塞等待决策，2 分钟超时按拒绝处理
3. 用户决策：`Decide(id, approve, scope)`，`scope=session` 时写入免审授权

**跨重启恢复（durable pause）**：

- 启动时 `RearmPending` 把未决记录的窗口延长到 24h，前端刷新后仍能拉到审批卡片
- 当进程内已无等待者（应用重启过），`Decide` 走 `decideFromRecord` 落库并触发 `kickResume` → `ResumeRun(runID)`
- 续跑从检查点恢复消息与步骤记忆；已决记录被消费后置 `consumed`，防止一次性审批被静默复用

**补问** `request_input` 走同一套机制（`Kind=input`），回复经 `Answer(id, text)` 回填。

**免审授权**：进程内表 + `approval_grants` 表；run 以 error/cancelled 收尾时回滚本 run 新增的授权（未验证的工作不留下扩权）。

## 目标模式

会话级目标（`MetadataJSON.goal`）：`active / paused / done`，含 `Text / Round / MaxRounds(20) / NextStep`。

`SetGoal(action)`：`set / pause / resume / clear`。Agent 每轮结束汇报是否达成，未达成则自动进入下一轮（上限 20）。这让「把所有 TS 错误修完」这类目标能自行推进，而不是一轮就停。

## 辅助对话

每个主会话可挂一个 `Kind=side` 的辅助会话（`EnsureSideConversation` 幂等创建），用于「不影响主线的追问」：它以主会话历史前缀为上下文（有界截取到 12000 rune，起点对齐 user 轮次，首条标注来源），不进侧栏列表。

## 上下文占用与压缩

`/context` 展示上下文分段占用（各 Section 的 token 估算）。触发压缩时后端做确定性折叠（见 [04-Agent内核](04-Agent内核.md)），把裁剪边界写入会话元数据并通知前端。

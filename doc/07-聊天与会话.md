# 07 · 聊天与会话

## 会话

`ChatSessionDO`：`ProviderID / Model / WorkspacePath / PermissionMode / Kind / ParentID / Pinned / MetadataJSON`。

- 权限四档 `restricted / default / auto_edit / yolo`，会话切换时同步后端
- `Kind = side` 是辅助会话（见下），不出现在侧栏列表
- 目标模式、压缩边界等会话级状态存 `MetadataJSON`，避免为每种状态加列
- 会话可绑定本地工作区目录；未绑定时用默认工作区（`{home}/workspaces/{sessionID}`，与文件面板同源）

## 一次发送的完整链路

`ChatService.SendStream(ctx, sessionID, content, fileIDs, params)`：

1. 取会话级锁（关键区只覆盖「占位落库 + run 登记」，跨会话互不阻塞）
2. 补齐 Provider/Model 兜底、解析附件（图片转多模态 part）
3. `prepareRun`：取消该会话遗留的挂起审批 → 分配序号（user + assistant 占位各一条）→ `runID` →
   登记执行平面 → 落 user 消息 + assistant 占位（`streaming`）
4. 建可取消 ctx 并登记到 `runRegistry`，立刻返回 `{run_id, assistant_msg_id}`
5. 后台 goroutine `runLLM` 继续：墙钟上限（Agent 定义或 10 分钟）

`runLLM → executeAgent` 的装配顺序：

```
技能同步 → Agent 模型/推理强度覆盖 → UserPromptSubmit 钩子（可阻断）
→ 取 Provider → 拉历史（含多模态）→ 辅助会话前缀 → 上下文装配（能力 Preload + 预算裁剪）
→ 工具两级过滤（技能白名单 → Agent 策略）→ 预算计算
→ newCoreLoop（Sink=事件映射，Hooks=插话/续跑，注入 Delegator 与 InputRequester）
→ RebuildHistory 清洗后 Run（或 Resume）
```

内核实例的依赖全部来自 `ChatDeps`（构造期一次性注入）：检查点存储、事件出口、审批门、目录信任、
计划模式状态、文件变更服务、消息块仓库——run 期间不存在「依赖取不到就静默跳过」的分支。

收尾：按每次上游调用落 `token_usages` → 写运行记录 → assistant 落库（正文/思考/工具调用/停止原因/用量/耗时）
→ 失败或取消时回滚本 run 新增的免审授权 → 反幻觉核验（声明改了哪些文件 vs 实际变更记录）
→ 能力沉淀 → 目标模式判定是否继续 → **发 `chat:done`（落库后才发）**。

## 消息与流式

消息角色：`user / assistant / tool / system`。`Seq` 会话内单调，工具消息与注入消息统一分配序号，避免撞号。

```
POST /chat/stream → 返回 run_id
GET /events?scope=chat&session_id={sid}&run_id={run_id}  ← SSE（会话级订阅）
```

订阅键是 `session_id`（会话内全部 run 与无 run 归属的事件都送达），`run_id` 供断线重放定位。
事件出口唯一：`service.Emitter`（注入归属 → 分配 seq → 写入重放缓冲 → 广播）；业务域不得自行 `bus.Publish`。

`chat:*` 事件由 service 的事件映射器产生（内核事件 → 前端协议），全量清单：

| 事件 | 触发 | 载荷要点 |
|---|---|---|
| `chat:stream.start` | run 建流 | `model`、`resumed`（续跑的新 run 也走这里） |
| `chat:stream` / `chat:thinking` | 正文/推理增量 | `delta` |
| `chat:turn-start` / `chat:stats` / `chat:checkpoint` | 轮次边界 | `turn`、用量、检查点位点 |
| `chat:tool` / `chat:tool-result` | 工具调用与回执 | `id`、`name`、`activity`、`duration_ms`、`data` |
| `chat:approval` / `chat:approval-decided` | 审批请求与决策 | `id`、`command`、`risk`、`can_remember` |
| `chat:todo` / `chat:goal` | 计划与目标状态 | `state` / `goal`（`chat:goal` 无 run 归属） |
| `chat:file-change` / `chat:artifact` | 变更与产出登记 | `change` / `artifact` |
| `chat:compressed` / `chat:context-trimmed` / `chat:warn` | 上下文与护栏提示 | 折叠条数、被丢段、告警类型 |
| `chat:retry` | 建流瞬时错误重试 | `attempt`、`delay_ms` |
| `chat:subagent-start/done/error` | 子 Agent 生命周期 | `sub_run_id`、`agent` |
| `chat:done` | run 终态（落库后发） | `domain.ChatDoneEvent`：`status/reason/stop_reason/message_id/usage` |
| `chat:error` | 运行错误 | `code`、`message` |
| `chat:gap` | 重放窗口被覆盖 | `run_id`、`last_seq` |

**终态模型**：`chat:done` 之后 SSE 连接**保持打开**（不关闭）。目标模式的自动续跑要先跑一次校验
LLM 调用（可能数十秒）再起新 run，保持连接才能无缝续看；其间 `chat:goal` 也会继续送达。
前端收到新 run 的 `chat:stream.start` 时重置流式累积，同会话重发消息时才替换旧连接。

## 审批与暂停恢复

工具策略门的 `ask` 决策落到 `ApprovalService`：

- **阻塞式等待**：聊天 run 的门阻塞当前 run 等用户决策（前端 `chat:approval` 卡片）
- **持久化**：未决记录落 `approval_records`；重启时 `RearmPending` 把窗口延长到 24h，前端刷新仍能拉到卡片
- **跨重启续跑**：进程内已无等待者时，`Decide` 落库并触发 `ResumeRun(runID)` → 从检查点恢复
- **一次性消费**：已决记录被消费后置 `consumed`，防止一次性审批被静默复用
- **授权回滚**：run 以错误/取消收尾时回滚该 run 扩出的「本会话允许」授权（未验证的工作不保留免审）

**补问** `request_input` 走同一套机制（`Kind=input`），回复经 `Answer(id, text)` 回填。

## 目标模式

会话可设一个目标（`/goal`），每轮 run 正常收尾后由独立的小型 LLM 调用**按实据校验**：
只有文件变更、命令输出、测试结果这类可核对产物才算达成；计划、清单、口头结论都不算。

- 未达成 → 携带「下一步动作」自动续跑下一轮（同一会话起新 run）
- 异常收尾（打断/出错/超轮次）→ 自动暂停，不盲目续跑烧 token
- 状态存会话元数据，随时可 pause / resume / clear

## 辅助对话（side）

右栏的并行问答：继承主会话历史（有界截取 + 对齐 user 轮次）但不进主时间线，
主对话被审批卡住时仍可用。`Kind=side` 的会话不出现在侧栏。

## 取舍

| 取舍 | 优势 | 代价 |
|---|---|---|
| 一次对话 = 一次 run（显式生命周期） | 中断、续跑、用量归属、审计都有明确边界 | 一次 run 内的并发只能靠工具层并行 |
| 会话级锁 + 插话（steer） | 跨会话天然并行；同会话中途纠偏不打断执行 | 同会话无法真正并行两个 run |
| 拒绝/审批可跨重启 | 用户不必重跑长任务；决策不会因崩溃丢失 | 需要持久化与重武装逻辑（多一张表与一组恢复钩子） |
| 目标模式用独立 LLM 校验实据 | 避免"看起来完成了"的假达成 | 每轮多一次模型调用（计入用量） |
| `chat:done` 后连接保持 | 目标续跑无缝；无重连抖动 | 一个空闲 SSE 连接常驻（有 30s 心跳） |

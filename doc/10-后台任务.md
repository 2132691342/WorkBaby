# 10 · 后台任务

后台任务解决的是「长活不该占着聊天窗口」：用户提交一段自包含的任务描述，立即返回，任务在后台跑完出结果，可取消、可查看、跨重启可见。

它与委派（`delegate_task`）的分工：

| | 委派 | 后台任务 |
|---|---|---|
| 触发 | 父 Agent 在 run 内主动调用 | 用户显式提交 |
| 同步性 | 同步阻塞，结果回传父 Agent | 异步，结果存库供查看 |
| 持久化 | 不落任务表 | 落 `chat_tasks`，跨重启可见 |
| 用途 | 拆分子问题 | 长作业（整理、批量修改、检索汇总） |

## 模型与状态机

`ChatTaskDO`（表 `chat_tasks`）：`ID / SessionID / Agent / Prompt / State / RunID / Result / Error / CreatedAt / StartedAt / FinishedAt`

```
pending ──► running ──► completed
   │           │
   └───────────┴──────► failed / cancelled
```

`SessionID` 是宿主会话：任务的工作区与模型都从它派生，所以任务必须绑定一个会话。
`TaskTerminal(state)` 判断终态。

## 执行

`ChatTaskService` 持有队列（容量 64）与 2 个 worker goroutine：

1. **Submit**：校验（描述非空、会话必填）→ 落 `pending` → 发 `task:created` → 入队。队列满立即失败并回写终态（背压直接暴露给用户，不静默滞留）
2. **worker**：取任务 → 终态跳过 → 会话缺失则快速失败 → 落 `running + runID` → 发 `task:started` → 执行 → 落终态并发 `task:done`
3. **Cancel**：终态幂等；`pending` 直接标记取消；`running` 触发该任务的 `CancelFunc`，由执行流程收尾

预算：墙钟 30 分钟、单次工具 5 分钟、默认 40 轮（Agent 定义可覆盖）。

**执行复用聊天同一条链路**：`core.Loop` + 完整护栏链（暴露 / Schema / 策略 / 用户钩子 / 重复熔断），工具集 = 全注册表 ∩ Agent 策略。差异只有两点：

- 事件出口是 `NopSink`（任务不向聊天窗口吐增量）
- 审批门换成 `grantApprover`

## 无人值守审批

后台任务没有人在旁边点「批准」，所以审批门是 `grantApprover`：

- `irreversible` 风险：一律拒绝（与聊天同一铁律）
- 其余：命中免审授权（`approval_grants`，即用户在聊天里批准过的命令）才放行
- 未命中：拒绝，并带可解释的原因（实现 `core.ApprovalReasoner`）——模型读到原因会改道或收束说明

这不是「跳过安全」：后台任务继承的是用户明确批准过的命令集合，未授权的一律不做。

## 事件与前端

后端发三类事件：`task:created / task:started / task:done`，载荷带整条任务对象。SSE Hub 订阅 `task:` 前缀，前端按 `scope=task` 订阅并整对象 upsert。

事件是通知不是真相源：重连后前端拉一次权威列表兜底。终态无论面板是否打开都弹提示。

前端入口：聊天页右栏「任务」tab（`TaskCenterPanel`，tab 按钮带活跃数徽标），`/tasks` 命令打开面板，`/agent` 命令弹窗提交。

## 用量与恢复

- 用量按 `UsageSourceTask` 单独落账（`Turn = -1`），仪表盘可按来源拆分
- 启动时 `recoverUnfinished`：把库里仍处于 `pending / running` 的任务统一标记失败（进程重启后它们不可能还在跑），避免留下永远转圈的任务

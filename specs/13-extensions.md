# 13 · 插件（扩展与包）

## 两套机制，不要混

| | 包（package） | 扩展（extension） |
|---|---|---|
| 形态 | 一个 npm / git / 本地目录 | 一个 `.ts` / `.js` 文件或目录 |
| 能力 | 扩展 + 技能 + 提示模板 + 主题，一次装齐 | 只有扩展 |
| 安装 | `pi install <source>` | 复制进 `extensions/` 并登记 |
| 记录在 | `settings.json` 的 `packages` | `settings.json` 的 `extensions` |
| 落地位置 | `~/.pi/agent/npm/node_modules/<name>` | `~/.pi/agent/extensions/<name>` |
| 界面动作 | 安装 / 卸载 / 看目录 / 看版本 / 更新 | 启用 / 停用 / 导入 / 删除 |

## 包

```
来源写法：npm:@scope/pkg[@ver] · git:github.com/owner/repo[@ref] · ./本地目录 · https://…
```

- 装 / 卸 / 更新都调 PI 自己的 CLI，WorkBaby 不重写一遍包的解析与版本规则；
- 输出按行回传（`chat:setup`）：npm 拉包可能几十秒，没有进度界面会被当成卡死；
- 同一时刻只允许一个装 / 卸 / 更新动作（并发 npm 会写坏同一个目录）；
- 清单里的包若目录不在，界面标「目录缺失」——静默消失会让人以为设置没保存；
- 包自带的技能随包装卸，技能页把它们标为「插件包」且不可搬动。

## 版本与更新

| 读的 / 做的 | 怎么做 |
|---|---|
| 本地版本 | 读包目录里的 `package.json`（npm 与 git 都要能读） |
| 最新版本 | npm 注册表的 `dist-tags.latest`；git 与本地目录不参与（它们的「新版」不是一个数字） |
| 更新一个包 | 把它重装到最新版：`pi install npm:<name>@<latest>` |
| 更新全部 | 逐个重装需要更新的 npm 包；git 包走 `pi update <source>`；本地目录不参与 |

**不走 `pi update --extensions`**：PI 会跳过固定版本（`npm:x@1.2.3`），而 `pi install`
写进 `settings.json` 的正是固定版本——那条命令会「成功地什么也不做」。

**npm 包必须带确切版本号**：包根目录的 `package.json` 里存的是 `^旧版本` 范围，
只写 `npm:<name>` 时 npm 会按这个范围装回旧版本（0.4 → 装不到 0.5）。
装完读一次包目录的 `package.json` 核对版本：不匹配就当失败报出来，不谎报「已更新」。

**结束信号**：`chat:setup` 的 `done` / `ok` 帧是唯一准绳，界面据此收 loading 并重新拉
清单与版本对账。用定时器猜结束会提前弹「已更新」，刷新后看到的还是旧版本。

**有对话在跑时拒绝**（9719）：装 / 卸 / 更新都要重启 PI 进程，跑到一半的回合会断，
与其让用户莫名其妙丢一轮，不如明说「先停下再更新」。

版本查不到不是错误：界面只不显示「可更新」。

## 扩展

- **登记表就是开关**：`settings.json` 的 `extensions` 里有它就是启用；
  文件不搬走——PI 只读登记表，搬目录会让「导入过的插件」在磁盘上反复挪位置。
- 支持通配条目（`!pattern` / `+path` / `builtin:*`）：界面把它们标为只读，
  不值得为几种 glob 语法写一个编辑器。
- 删除 = 删磁盘文件 + 摘登记项。

## 生效时机

扩展与包都是**启动期加载**的：

```
改登记表 → 写 settings.json → 重启全部 PI 进程
```

因此界面上每个改动都会触发一次重启。重启会中断正在跑的对话——这是「改了就有用」的代价，
比起「改了没反应」更容易解释。

## 插件市场

发现机制不归 WorkBaby 发明：PI 官方的包画廊来自 npm 关键字 **`pi-package`**
（带这个关键字的包才进 pi.dev 的画廊）。市场页按这个关键字搜 npm（`/-/v1/search`，
官方源与镜像同一形状、同一套双源回退与短缓存），对账本地已装清单后展示：
名称、描述、最新版本、发布者、发布时间、已装标记。安装就是把 `npm:<name>`
交给上面那条装包链路——市场只是发现层，不引入第二套包规则。

注册表连不上不是失败：清单给空、`error` 带原因，已装插件的管理不受影响。

## 与 PI 的分工

| 事 | 谁做 |
|---|---|
| 包的解析、安装、依赖、模块映射 | PI |
| 扩展的加载与执行 | PI |
| 列出条目、翻译开关、流式回传进度 | WorkBaby |

## 取舍

- **调 CLI 而不是自己 npm install**：PI 的包规则会演进（模块映射、peer 抑制、git reconcil）；
  跟着它走永远不会分叉，代价是装包依赖 PI 已就绪。
- **登记表启停**：可逆、可脚本化；代价是停用后文件还在磁盘上（这正是「还能再启用」的前提）。
- **一次一个装包动作**：安全；代价是用户要排队。
- **市场只做发现、装卸复用同一条 CLI 链**：永远跟 PI 的包规则同源；代价是市场内容取决于 npm 上带 `pi-package` 关键字的包有多少（生态早期可能就几条，空态要把这一点说清楚）。

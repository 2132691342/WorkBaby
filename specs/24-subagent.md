# 24 · 子代理

## 定位

一件可以独立完成的活，交给一个单独的助手去跑，只把结论拿回来。

它的价值不在「又一个能干活的」，而在**上下文纪律**：读十个文件确认一件事，
那些原文留在主对话里就是十份永久占位——之后每一轮都要为它们付 token，还会更早撞上压缩。
子代理在自己的隐藏会话里读完，只回一句结论。

**它是提示词与工具集的组合，不是新运行时**：子会话走的是同一个 `ChatService`，
同一套审批闸门、同一个事件出口、同一本用量账、同一套输出截断。

## 设计

| 决策 | 选择 | 为什么 | 代价 |
|---|---|---|---|
| 触发方式 | 主助手自己决定（`subagent` 工具） | 「什么时候拆活」是语言判断，写死规则会拆错；且用户不该被迫学「怎么开子代理」 | 模型可能不用它，或拆得过碎 |
| 载体 | 第二个 PI 进程里的隐藏会话 | 复用全部会话基础设施（条目链 / 用量 / 事件 / 审批），用户看不到乱账 | 多一个 Node 进程（~150MB），所以子代理必须串行 |
| 返回形态 | 一段文本（含失败原因与用量） | 失败也回文字：让模型看到「这一步没做成」比抛错中断整轮更有用 | 结论是自然语言，不是结构化数据 |
| 工具白名单 | 可选，只减不增 | 收窄能省预算、防误操作；但全局停用的工具在这里填了也开不回来 | 收窄错了它就做不成（提示里已警告） |
| 权限档 | 继承父会话 | 子代理不是提权通道 | 父会话是 `ask` 时，子代理照样会停下来等审批 |
| 工作目录 | 继承父会话 | 它要处理的就是同一摊文件 | 做不了「换个目录」的活 |
| 并发 | 每次调用一个子代理，串行 | 一次一个是可以预期的；并行会把「谁在花钱」变成一团 | 多件独立活要多次调用 |
| 超时 | 20 分钟 | 子代理跑飞了不能拖着父会话一起等 | 长活做不完（该拆成更小的步） |
| 上下文 | 子代理看不到父会话 | 显式传背景比隐式继承可预测：继承会让子代理莫名其妙带上无关历史 | `task` 必须写清背景与期望产出 |

### 事件与观测

子代理跑在**另一个 PI 进程**里，因此它的进程级事件与父会话物理隔离，
不存在 seq 竞争。翻译层把它的 `chat:*` 投到隐藏会话那条流上，父会话里它只表现为
一张工具卡（`subagent`），卡片展开是它的结论。

**为什么必须是另一个进程**：一个 PI 进程只有一个 streaming 状态。在同一进程里
起子会话会把父会话的流式输出顶掉——那是个阻塞而非并发。

代价：每跑一次子代理多一个 Node 进程（~150MB）。所以子代理**串行**：
一次调用一个，跑完即 kill。这个代价是明确的，也是「串行」这条限制的真正原因。

## 契约

`subagent` 工具：

```jsonc
{
  "task":  "要子代理做的事，含必要背景与期望产出的形态",   // 必填
  "label": "这一步的短名字，给用户认",                      // 可选
  "tools": ["web_search", "read"],                          // 可选，不填沿用当前启用集
  "model": "另一个模型名"                                    // 可选，不填跟随当前会话
}
```

返回（给模型的那一份）：

```
<子代理的结论正文>

（子代理用量 12345 tokens）
```

失败时返回一句人话加原因：

```
子代理失败：上游 429，请求太频繁
子代理超时（20m0s）没有收尾，这一步没做完。
子代理没有产出结论
```

`tools` 是筛子不是授权：它只能在「全局启用集 ∩ 父会话白名单」里再收窄一层。

## 关键流程

1. 主助手在某轮里发起 `subagent` 调用（参数校验走 JSON Schema）
2. `SubagentService.Run`：校验任务非空（`5103`）→ 读父会话 → 建隐藏子会话
   （沿用工作目录 / 权限档 / 可选模型与工具白名单）
3. 挂旁听（采时间线与错误原因）→ `ChatService.Send` 起子 run
4. 等收尾：`WaitRun` 的完成信号，20 分钟上限，或父 run 被取消
5. 收尾：取子会话最后一条助手正文 + 用量，拼成结论返回
6. 父会话把结论作为工具结果回填，模型据此继续

子会话的失败不抛错给内核，而是回一段带原因的文本——**工具失败必须带原因**，
模型才知道该换方案还是该放弃这一步。

## 不变量

| 不变量 | 锁死原因 |
|---|---|
| 子会话不进用户会话列表 | 列表里出现一堆来路不明的会话就是乱账（`hidden=true` 过滤） |
| 子代理必须用独立的 PI 进程 | 一个 PI 进程只有一个 streaming 状态，同进程起子会话会把父会话的流顶掉 |
| 子代理复用同一审批与权限档 | 它不是提权通道；子代理的写操作照样要问 |
| 权限档与工作目录继承父会话 | 换成全局默认会让「我在这个文件夹里说的话」在子代理处失效 |
| 工具白名单只减不增 | 全局停用的工具，子代理开不回来 |
| 失败必须带原因 | 只回「失败」的话，模型唯一能做的是重试同一个调用——而它多半还会失败 |
| 父 run 取消必须停掉子 run | 否则用户在界面上停了，后台还有一棵在烧 token 的子树 |
| 超时必须停掉子 run | 超时只回报不停止，等于留一个无人收尾的 run |
| 子代理进程必须在收尾时 kill | 不 kill 就是用户每用一次子代理就永久漏一个 Node 进程 |
| 结论里必须带用量 | 父助手要判断「这一步贵不贵、还要不要继续拆」 |
| 子会话同样计用量、同样受保留期归档 | 子代理不是绕过计量与归档的通道 |

## 取舍

- **不转发子代理事件到父流**：省掉一套「多源事件合流 + 按来源分组」的前端复杂度；
  代价是对话里看不到子代理的实时过程，只能看结论与「运行」页签的历史。
- **串行而非并行**：一次一个能说清「现在在花钱的是哪一步」；代价是多件独立活要串起来等。
- **不带结构化返回值**：任务间传的是自然语言，换来任意任务可组合；
  代价是模型要自己从结论里挑它需要的部分。
- **不用它替代「多步任务」**：子代理是一次委派，没有依赖图、没有评审门。
  真需要「A 做完再做 B」时，那件事本来就该在同一轮对话里说清楚——
  为一个办公场景引出工作流引擎，维护成本与概念负担都会翻倍。

# 12 · 后台任务

后台任务把「提交即返回、跑完出结果」的异步 Agent 作业从主对话中分离出来：
长任务不必占着会话，与前台聊天可并行。

## 1. 状态机

```
pending → running → completed / failed / cancelled
```

应用重启时未终态任务统一标记失败（没有进程能继续跑它们）。

## 2. 执行模型

| 维度 | 实现 |
|---|---|
| 队列 | 容量 64 |
| Worker | 2 个并发 |
| 取消 | per-task `CancelFunc`（`pending` 直接取消；`running` 触发 ctx 取消；幂等） |
| 宿主会话 | 每个任务挂在一个会话上（`SessionID`）：工作区与模型来源都取自它 |
| 护栏链 | **复用聊天同一套**（工具注册表、护栏中间件、事件出口） |
| 审批门 | `grantApprover`：只吃免审授权，**不弹窗**（无人值守场景不能挂起） |

**为什么复用护栏链**：后台任务与前台聊天的唯一差别是「谁来回应审批」，
其余安全语义（暴露清单、注入检测、路径信任、熔断）必须完全一致。

## 3. 提交与查询

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/tasks?limit=50` | 任务列表（最新在前；items + total） |
| POST | `/tasks` | 提交（body: `session_id` / `agent` / `prompt`；返回 pending 任务） |
| POST | `/tasks/:id/cancel` | 取消（幂等） |

实时变化经 `task:created` / `task:started` / `task:done` 事件（`scope=task` 独立订阅）。

## 4. 与前台对话的隔离

| 维度 | 前台 run | 后台任务 |
|---|---|---|
| 活动 run 槽 | 占用（`runRegistry`，同会话串行） | **不占用**（可与前台并行） |
| 事件 scope | `chat` | `task` |
| 审批 | 阻塞等待用户（`chat:approval` 卡片） | 只吃免审授权 |
| 结果 | 落 assistant 消息 | 落任务记录（`Result` / `Error` 字段） |
| 用量归因 | `UsageSource = chat` | `UsageSource = task`（成本单独归因） |

## 5. 结果与恢复

| 项 | 处理 |
|---|---|
| 成功 | 状态 `completed` + `Result` 存摘要 |
| 失败 | 状态 `failed` + `Error` 存原因 |
| 取消 | 状态 `cancelled`（已产生的副作用保留，文件变更仍可回滚） |
| 重启 | 未终态 → `failed`（原因写明进程中断） |

## 6. 取舍

| 取舍 | 优势 | 代价 |
|---|---|---|
| 队列 + 固定 worker 数 | 资源可控，不会因大量提交耗尽 goroutine | 大并发时排队（容量 64） |
| 复用聊天护栏链 | 安全语义一致；实现收敛 | 需要一套 `chat.ChatService` 之外的可注入审批门 |
| 后台任务不占活动 run 槽 | 与前台对话可并行 | 同会话内可能出现「前台 run + 后台任务」并发执行（各自的工作区写操作仍需用户判断） |
| 无人值守审批门只吃免审授权 | 不会挂起等一个不会到来的决策 | 需要用户事先授权（否则任务只能做免审操作） |
| 重启标记失败而非恢复 | 实现简单、语义明确 | 用户需重新提交（长任务无自动续跑） |
| 用量按来源归因 | 成本可分开看（对话 vs 任务） | 每个记费点都要正确标注来源 |

# 22 · 记忆（长期事实与偏好）

## 定位

记忆是「跨对话仍然成立」的那部分上下文。会话结束即归档，知识库装的是文档，
技能装的是做法，都不回答「这个人是谁、他习惯怎样」。记忆回答这一条。

它不单独成包：模型在 `domain/memory.go`、存储挂 `repo/memory.go`、
编排在 `service/memory.go`——与运行观测同一套惯例，
一个只有一张表的能力不值得开一个目录。

## 设计

| 决策 | 选择 | 理由 | 代价 |
|---|---|---|---|
| 载体 | 一张 `memories` 表，不建 FTS 虚表 | 记忆总量上限 200 条，全量读出的成本远低于维护一套索引与触发器 | 不能用关键词检索记忆，只能全量注入或界面上翻 |
| 注入方式 | 每条对话组装系统提示时读一次，按最近更新取前 30 条、总字数封顶 2000 | 记忆必须「自动生效」——靠模型想起来才去查，等于没有 | 每轮多一次读表；提示词里固定占一小块额度 |
| 写入入口 | 两条：界面手写的（`manual`）、助手用 `memory_write` 记的（`auto`） | 用户从不主动维护记忆，入口必须在助手这一侧 | 助手可能记下不该记的，靠工具准则与界面可删除来兜 |
| 去重 | 内容完全相同只刷新 `updated_at` | 模型记不住自己说过什么，同一件事记十遍会吃满提示额度 | 措辞不同的重复记不住，只能靠删 |
| 生效开关 | 停用不删除 | 「不想让它提这件事」和「彻底忘了」是两件事 | 表里留着不生效的行 |

**为什么不做自动摘要**：会话结束时让模型再跑一轮「这次有哪些值得记住的」，
等于每次对话多一次完整调用，而且它总结出来的多半是本次任务的细节而不是长期事实——
长期事实的标志是用户明确说过，这个信号只有用户和「记住…」这句话能给。

## 契约

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/memories` | 记忆列表（新的在前），`{items[]}` |
| POST | `/api/v1/memories` | 新增 `{content}`，标为 `manual` |
| POST | `/api/v1/memories/update/:id` | 改内容或开关 `{content?, enabled?}` |
| POST | `/api/v1/memories/delete/:id` | 删除 |

出参 `MemoryVO`：`{id, content, source, enabled, created_at, updated_at}`。
`source` 取 `manual`（用户在界面上写的）/ `auto`（助手记的），界面上分得开。

工具 `memory_write`：`{content}` → 写一条 `auto` 记忆，不需要审批
（写的是本地一张表，风险低于跑命令；界面上随时能删）。

约束常量：单条 ≤ 500 字，总量 ≤ 200 条，注入上限 30 条 / 2000 字。

错误码 9501–9505，见 `docs/ERROR-CODES.md`。

## 关键流程

1. 用户说「记住，我们报表标题都用深蓝色」→ 模型调 `memory_write` → 落库标 `auto`
2. 下一轮对话：组装系统提示时 `RenderForPrompt` 读出启用的记忆 → 拼进「记住的这些事」
3. 用户在设置页「记忆」面板手写一条 → 标 `manual`；可改、可停用、可删

## 不变量

| 不变量 | 锁死原因 |
|---|---|
| 注入永远按条数与字数双封 | 只封其一就会被几条超长的或几百条短的顶穿提示额度 |
| 读取失败只告警不拦对话 | 记忆是增强，读不出来不该让助手开不了口 |
| 内容完全相同的只更新时间 | 不去重的话提示额度很快被同一句话占满 |
| 模块名 / 包名进入命令前必须校验字符集 | 名字要拼进 shell 命令，不校验等于敞开命令注入面 |

## 取舍

- **全量注入而非检索**：省掉一套索引与触发器，代价是记忆多了之后前 30 条之外的
  事实上不了桌。200 条上限把这个代价压住了——真需要放几百条事实时，该用的是知识库。
- **助手可写**：记忆真正有用的前提是有人往里写，而用户不写；
  代价是可能记进不该记的，靠工具准则（不记密钥、不记过程）与界面删除兜底。
- **不自动摘要**：省掉每次对话的一轮额外调用，
  代价是「用户没说过但确实反复出现」的偏好不会被自动发现。

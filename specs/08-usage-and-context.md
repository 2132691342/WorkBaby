# 08 · 用量与上下文水位

## 定位

两件「看得见」的事：这次对话还能聊多久（上下文水位）、
这个月在模型上花了多少（用量统计）。两者都不是给工程师看的诊断信息，
是给办公用户做决策的依据——「要不要开新对话」「这个模型是不是太贵」。

## 上下文水位

### 数据来源

水位不再由 WorkBaby 自己算。PI 在事件里直接给：

| 来源 | 给什么 |
|---|---|
| `message_update.usage` | 本轮实时 usage（input / output / cacheRead / cacheWrite / totalTokens / cost） |
| `get_session_stats` | 会话累计：token、cost、消息数、上下文占用 |
| `turn_end` | 本轮结账点 |

`tokensBefore` / `tokensAfter` 来自 `compaction_end`，用于“压缩了多少”的展示。

- `context` 取 PI 报的当前上下文占用；窗口取 `models.json` 里该模型的 `contextWindow`
- 窗口未知（模型未声明）时不给百分比，只给绝对数并标「约」
- 给模型输出的余量取 `maxTokens`，与 PI 的压缩参数 `reserveTokens` 同源

**WorkBaby 不再有本地 token 估算器**。估得再准也是第二份口径，
与 PI 真正发出去的数字不一致时，界面会显示「没满」而 PI 已经开始压缩。

### 为什么每轮都发

只在「真的压缩了」时才发不够：用户需要的是**水位上涨的过程**，
等它涨满了才知道就晚了。事件很轻（一条整数），不构成负担。

### 展示口径

- 输入框底栏常驻一枚水位环 + 读数（`已用 / 窗口`），0% 也显示——
  什么都不显示等于用户没有这个信息
- 打开 / 切换 / 新建会话时从 `get_session_stats` 回填，不必等下一轮 `chat:context`
- 压缩发生时插一条分隔提示：「已压缩（12.4万 → 2.1万）」
- 一轮结束时用 `message_end` 带回的权威 usage 再校准一次水位：`message_update`
  报的 `context` 是**这一轮开始前**的占用，不含刚写出的回复本身，差的那截在 `done` 时补上
- **环的分母是可用预算**（`窗口 - 余量`），不是整窗口：内核在 `before > 窗口 - 余量`
  时就动手整理，用整窗口当分母会慢半拍——整理已经发生、环上才 87%，用户看着
  「还有空间」却在丢内容。所以 `ratio` 到 100% 的含义是「下一轮就要整理」
- 悬停提示报出整理线（`窗口 - 余量` 的具体 token 数）：「该开新会话了」得能落到数字上
- ≥80% 转警告色，≥95% 转危险色（按可用预算算，颜色与整理线一致）
- 窗口为估算值时读数加「约」前缀；估算值本身偏保守，宁可让用户早一点决定开新对话

## 用量统计

### 数据来源

`token_usages` 表，每次 LLM 调用一行（`session_id` / `entry_id` / `provider` / `model` /
`input` / `output` / `cached` / `total` / `context` / `latency_ms` / `created_at`）。会话表上另有 `total_tokens`
冗余计数，删除会话时级联清理。

### 口径

三处读数（消息底部、会话累计、仪表盘）必须同源同口径，否则同一件事会出现三个数。
字段直接采用 PI 的 `Usage`：

| PI 字段 | 落库列 | 口径 |
|---|---|---|
| `input` | `input` | 这一次请求的**全部**输入 token。PI 已按协议归一，不再二次换算 |
| `cacheRead` | `cached` | 输入里命中上游缓存的部分，恒 ≤ `input`。命中率 = `cached / input` |
| `output` | `output` | 输出 token；PI 的 `reasoning` 已含在里面，不重复加 |
| `totalTokens` | `total` | 上游给的总量；小于 `input + output` 时以两者之和为准 |
| `cost.total` | `cost` | 上游按模型单价算出的美元成本；模型未声明价格时为 0 |
| `get_session_stats` | `context` | 会话当前上下文占用 |

`cacheWrite` 不单独建列：它不进命中率（命中率只关心读回来的部分），
要看的时候从 JSONL 的 `usage` entry 里找得到。

读数一致性是硬要求：用户看到的 `入 9.9K` 与 `上下文 9.9K` 必须真的是一回事。

**成本直接取 PI 的 `cost`**，WorkBaby 不自己算：单价在 `models.json` 里声明，
PI 按它的表算得比我们准。模型没声明 `cost` 时全为 0，界面把钱相关的卡片隐藏
而不是显示一堆 0——显示 0 会让人以为真的没花钱。

### 接口

`GET /api/v1/stats?days=14`，一次返回全部，前端不拼接口：

| 段 | 用途 |
|---|---|
| `totals` | 总量卡片：输入 / 输出 / 缓存命中量 / 总 token / 调用次数 / 会话数 / 总耗时与平均耗时 / 缓存命中率 / 平均与峰值上下文 / 总成本 |
| `daily` | 每日一柱，长度恒等于 `days`，**没有调用的天补零** |
| `models` | 按模型归因（含 cached），按消耗从多到少，最多 8 个 |
| `sessions` | 用量最高的 5 个会话，供跳转 |

缓存命中量是长对话真正的成本指标（`cached / input`）；平均与峰值上下文
回答「平时一轮有多重、最重的一轮是多少」，是判断「该不该开新会话」的依据。

补零是硬要求：否则 x 轴刻度会随「哪天恰好没说话」而跳动，
用户会以为数据出错了。

### 聚合口径

- `days` 缺省 14，上限 90
- 起点取当天往前 `days-1` 天的本地零点，`localtime` 归组——用户看的是自己的日历
- 平均耗时 = 总耗时 / 调用次数，避免「今天没说话」时均值被拉成 0
- 上下文用量只统计 `context > 0` 的行：没记下上下文占用的调用若计入，会把均值与峰值一起拉低

## 取舍

不做趋势预测、不做预算告警。这两样都需要用户额外配置阀值，
对本机个人助手是纯负担。把已经发生的量说清楚，就够用户做
「换不换模型」「要不要清一清」的决定了。

代价是**给不了「这次对话还够聊几轮」的直接结论**：水位环只报占用比例，
换算成轮数要用户自己看数字。给出估算轮数需要假设每轮长度，而每轮长度差异极大
（一句问答与一次多文件批处理差两个数量级），猜出来的轮数比不给更误导。
另一个代价是统计口径依赖本地时间：跳时区或改系统时间后，历史分组会跟着变。
成本列依赖模型声明单价：用自定义端点且没填 `cost` 时，钱卡片整块消失。

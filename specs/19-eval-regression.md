# 19 · 评估与回归

## 定位

评估回答「这次干得怎么样」：一次 run 收尾时记录它的客观指标（token / 耗时 /
工具成功率 / 是否被人打断），加上用户或模型给的主观分，成为一条评估记录。
回归回答「退步了没有」：把某次评估存为基线，之后同一条会话再跑与基线对比——
分数掉了、用量涨了、工具失败多了，一眼看见。

两者共用一套「运行证据」：评估记录引用的就是那次 run 的隐藏会话，
不是另存一份快照——证据只有一份，避免「记录里的」与「真实发生的」对不上。

## 设计

| 决策 | 选择 | 为什么 | 代价 |
|---|---|---|---|
| 评估对象 | run（每次对话的每一轮） | 一次执行是最小可评估单元 | 评估维度受 run 记录粒度限制 |
| 指标来源 | 客观指标自动采集，主观分人工或模型补 | 客观项不该靠人填；主观项不该假装客观 | 记录有两种来源，界面要分清 |
| 评分制 | 1–5 分 + 可选一句批注 | 五档足够表达「不能用 / 勉强 / 好」；百分制是精度幻觉 | 粗 |
| 基线 | 一次评估可存为基线（按会话归类） | 「这类活的好标准」是因事而异的 | 基线会过时，要能重新设 |
| 对比输出 | 分数差 / 用量差 / 失败步骤差 / 结果摘要并排 | 数字差最刺眼；摘要差给人看 | 摘要是文本，diff 只能并排 |
| 存储 | 评估与基线各一张表，run 只存引用 id | 评估可删可改不影响 run 本身 | 多一层关联 |

### 客观指标（自动）

| 指标 | 来源 |
|---|---|
| 输入 / 输出 / 缓存命中 token | `token_usages` 聚合 |
| 耗时 | run 起止时间戳 |
| 工具调用次数 / 失败次数 | 该会话 tool 结果条目 |
| 是否触顶（stop=length） | run 收尾状态 |
| 人工干预次数（审批 / 插话 / 停止） | 审批决策 + 队列记录 |

## 契约

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/evals?scope=&scope_id=` | 评估列表（按对象过滤） |
| POST | `/api/v1/evals` | 登记主观分 `{run_id, score, note?}`（客观指标自动带上） |
| GET | `/api/v1/evals/baselines` | 基线列表 |
| POST | `/api/v1/evals/baselines` | 存基线 `{eval_id, scope}`（session） |
| POST | `/api/v1/evals/baselines/delete/:id` | 删除基线 |
| GET | `/api/v1/evals/compare?baseline_id=&run_id=` | 单次对比 → 指标差 + 摘要并排 |

错误码：`9221` 评估记录不存在；`9222` 同一个 run 重复登记（改分走 update）；
`9223` run 不存在或没有可采指标；`9224` 基线不存在；`9225` 对比双方缺一。

## 关键流程

1. 一次 run 收尾 → 客观指标自动成记录（无主观分时状态 `auto`）
2. 用户在指挥台评估页给它打分写批注 → 状态 `rated`
3. 把一条 `rated` 记录存为基线（归类到这条会话）
4. 之后同对象的新 run 收尾 → 评估列表里自动出现「对比基线」列：分数差 / 用量差
5. 点开对比页：指标差 + 两次结果摘要并排 + 跳转各自隐藏会话的入口

## 不变量

| 不变量 | 锁死原因 |
|---|---|
| 一个 run 最多一条评估记录 | 一对多会让「哪次算数」变成扯皮 |
| 客观指标只读，不许手改 | 手改过的「事实」比没有事实更糟 |
| 基线引用评估 id 而非拷贝数值 | 基线要能看出「当时的那次」到底是什么样 |
| 删除 run 不删评估（标记失效） | 评估是账；删账要看得出删过 |

## 取舍

- **不做自动评判（不调 LLM 打分）**：自动分看似省事，实则把「模型觉得好」
  当成「用户觉得好」，还多花 token；主观分留给用户，模型批注可选。
- **指标止步于可自动采集项**：正确性 / 完整性这类真问题自动判不了，
  假装能判的仪表板比没有更误导。
- **回归 = 与基线对比而非历史趋势**：办公场景是「这次和上次比退步没有」，
  不是「画出 30 天分数曲线」；趋势图等评估数据厚了再说。

# 21 · Harness 控制面

## 定位

内核跑起来之后，用户面对的是三件事：**这一轮发生了什么、花了多少、退回去从哪来**。
对话页只答「此刻」，控制面答「全程」——它是仪表盘与控制台两块界面共用的后端。

本篇是总纲，把散在四篇里的数据收成一张图：

| 篇 | 负责什么 | 本篇怎么用它 |
|---|---|---|
| [15](15-runs-and-checkpoints.md) | run 记录、时间线、检查点、归档 | 控制面的主体数据 |
| [11](11-eval-regression.md) | 评估、基线、对比 | 「比上次好还是坏」 |
| [08](08-usage-and-context.md) | 用量聚合、上下文水位 | 「花了多少」 |
| [17](17-pi-supervisor.md) | 事件从哪来 | 所有记录的唯一起点 |

**它是只读投影，不是第二份执行态**：控制面里没有任何东西能改变一轮对话的行为。
唯一的写操作是评估打分与基线保存，那是人对结果的标注，不是对内核的指令。

## 数据流

```text
PI 进程
  └─ stdout JSONL ─► 翻译层 ─► service.Emitter ─┬─► SSE（对话页实时）
                                                └─► 旁监听者（只读）
                                                      ├─ Runs.Start / Finish
                                                      ├─ Checkpoints.Mark / Touch
                                                      ├─ token_usages 落袋
                                                      └─ Evals.Auto / Archive.Maybe
                                                        └─► SQLite
                                                              └─► /runs · /checkpoints
                                                                  /evals · /stats
```

旁监听者（`service/observe.go`）只从事件流抄数据：不改会话、不批审批、
不碰 PI 的任何状态。它坏掉的表现是记录缺一条，而不是对话走偏。

## 契约

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/runs?session_id=&limit=` | run 列表（不带 `session_id` 即跨会话，上限 200） |
| GET | `/api/v1/runs/:id` | 详情：记录 + 时间线 + 上下文快照 + 检查点 |
| GET | `/api/v1/checkpoints?session_id=` | 一个会话的全部检查点（按轮次倒序） |
| POST | `/api/v1/checkpoints/fork/:id` | 从该轮重开一条新会话 |
| GET | `/api/v1/evals?scope=&scope_id=` | 评估列表（可按会话 / 全局过滤） |
| POST | `/api/v1/evals` | 登记主观分 `{run_id, score, note?}` |
| GET | `/api/v1/evals/baselines` | 基线列表 |
| POST | `/api/v1/evals/baselines` | 存基线 `{eval_id, scope}` |
| POST | `/api/v1/evals/baselines/delete/:id` | 删基线 |
| GET | `/api/v1/evals/compare?baseline_id=&run_id=` | 单次对比：指标差 + 摘要并排 |
| POST | `/api/v1/archive` | 手动按保留期回收 |
| GET | `/api/v1/stats` | 用量聚合（按天 / 按模型 / 按会话） |

**回放端点不存在**：它复用 `GET /api/v1/runs/:id` 返回的 `timeline`（每步的 `at` 与 `ms`
都是现成的），播放器在前端按时间轴重排即可，不需要后端多给一次状态。

`GET /api/v1/stats` 是仪表盘两个图与四张计数卡的唯一数据源；
它聚合的是 `token_usages` 与 `runs`，不重新解析 JSONL——聚合口径必须与对话里
逐条显示的用量一致，否则用户会看到「这一轮 12k，仪表盘说 0」。

## 关键流程

1. 一轮对话开始 → `runs` 插入 `running`，同时按 PI 的 entry id 打检查点
2. 对话进行 → 每轮结束时覆盖写上下文水位 + 快照；每条 `message_end` 记一行用量
3. `agent_settled` → run 收尾（成功 / 失败 / 打断三种去向）+ 自动评估 + 按需归档
4. 用户进仪表盘 → 四个计数卡（总 token、输入/输出、缓存命中率、平均耗时）+ 一张趋势图 + 两张分布卡
5. 用户进控制台 → 看某次 run 的时间线、某轮的水位、从某个检查点分叉

## 不变量

| 不变量 | 锁死原因 |
|---|---|
| 记录全部由事件流投影，无独立写入口 | 两处可写就会有两处不一致，用户无法判断哪个是真的 |
| 正文只存一份（PI 的 JSONL） | `runs` 与快照只存指标；复制正文要在两处保持一致，不一致时无从判断 |
| `can_resume` 只在 `failed` / `aborted` 为真 | 正常结束的轮次「接着做」没有意义 |
| 检查点是 PI 的 entry id，不是消息快照 | 会话是树；回到某轮 = 让 PI 从该 id 分叉，压缩消息等于把树拍平 |
| 自动评估不重复记 | 收尾事件可能重投，重复记会让「哪次算数」变成扯皮 |
| 归档只删消息链，保留 run / 用量 / 评估 | 用量与评估是账；删了账就无法复盘 |
| 归档后 `runs.session_id` 置空 | 留着指向已删会话的 id，用户点进去就是 404 |

## 取舍

| 取舍 | 得到 | 失去 |
|---|---|---|
| 只投影，不代理执行 | 控制面坏了不影响对话 | 不能从控制面重跑一轮（重跑 = 新会话） |
| 无独立事件存储 | 一个真相源，无同步问题 | 时间线是读时投影，长会话有开销（单会话几百条可忽略） |
| 回放复用时间线，不另存快照 | 一个真相源，无同步问题；播放 / 单步 / 倍速都只是把既有数字按时间重排 | 回放只到「哪个动作、多久、成没成」，不复现当时的正文内容 |
| 聚合口径与逐条显示同源 | 仪表盘与对话对得上 | 不能用更省事的预统计表（那要多一条同步链路） |

**回放不另存快照**是有意的：完整回放要求把每个事件点的全部状态留下来，
而状态的大头在内核的上下文里，本机存一份就是第二份真相。
时间线里已经有 `at` 与 `ms`，把它按时间轴重走一遍就够了——
播放 / 单步 / 0.5×–4× 倍速都只是同一批数字的另一种排布。

它的边界要说清：**回放回的是「哪个动作在第几秒发生、花了多久、成没成」**，
不是「当时屏幕上显示了什么」。要看正文，去对话记录或运行记录的明细。

# 21 · 项目架构图

## 定位

打开一个代码项目，这里回答「它由什么组成、谁依赖谁、入口在哪」：本地静态分析
源文件的模块划分与 import 关系，画成一张分层依赖图。全部本地计算，不调模型、
不联网——「项目结构」这件事本来就该由解析器回答，问 LLM 又慢又贵还会编。

分析范围限工作目录（与助手干活的同一个目录），只读：一个字节都不写。

## 设计

| 决策 | 选择 | 为什么 | 代价 |
|---|---|---|---|
| 分析方式 | 正则解析 import / require 语句（JS / TS / Vue / Go） | 无语法树依赖，单文件完成；桌面端项目规模够用 | 动态 import / 字符串拼路径识别不了，标注覆盖率 |
| 图布局 | 按依赖深度分层（入口在顶，叶子在底），同层横向排 | 分层布局确定性强、可复现；力导向布局每次刷新都跳 | 边多时交叉难免，用高亮替代全部展开 |
| 节点粒度 | 目录即模块（单文件项目退化为文件） | 「模块」是人的认知单位；文件级图在大项目里是毛线 | 目录内关系看不到，点进去下钻 |
| 渲染 | 自绘 SVG（节点 + 贝塞尔连线） | 与全站设计语言同源：色值走令牌、无图形库依赖 | 交互（缩放 / 拖拽）自己实现 |
| 持久化 | 不落库，每次进页面重算（限时 10s） | 代码在变，快照必然过期；重算有上限兜底 | 大项目首次进入有感知延迟（出进度） |
| 指标 | 每个模块显示文件数 / 行数 / 被依赖次数 | 「谁是被大家依赖的地基」一眼可见 | 行数含注释，只作量级参考 |

### 覆盖的语言与深度

| 语言 | 分析深度 | 依据 |
|---|---|---|
| TypeScript / JavaScript | import 关系（含 `.vue` 的 script 块） | 前端项目主力 |
| Vue 单文件 | `<script setup>` 的 import + 组件使用关系 | 本项目自身就是 |
| Go | import 关系（包粒度） | 后端项目 |
| 其他 | 文件级索引（无依赖边） | 不猜格式 |

界面明示覆盖率：「N 个文件的 import 可解析，M 个为动态引用未解析」——
把工具的边界画出来，比画一张貌似完整的图负责。

## 契约

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/archmap/analyze` | `{path?}`（默认当前工作目录）→ 图数据 |
| GET | `/api/v1/archmap/entrypoints` | 入口文件清单（main / index / App 等） |

图数据形态：

```
ArchGraph{ root, nodes[{id, label, files, lines, indegree, depth}], edges[{from, to}], coverage{parsed, dynamic, skipped} }
ArchEntrypoint{ path, kind(main|index|app|config), label }
```

错误码：`9401` 目录不存在或不可读；`9402` 不是代码项目（没有可解析文件）；
`9403` 分析超时（结果可能不全，明说）；`9404` 扫描文件数超上限（10 万）。

## 关键流程

1. 指挥台架构页 → 选目录（默认工作目录）→ 分析（进度条，限时 10s）
2. 出图：分层节点 + 依赖边；入口节点带标记；被依赖多的节点视觉加重
3. 点节点 → 侧栏显示该模块的文件清单 / 行数 / 依赖了谁 / 被谁依赖
4. 覆盖率与限制一行写明；不支持的语言退化为文件节点

## 不变量

| 不变量 | 锁死原因 |
|---|---|
| 只读，不写项目任何文件 | 分析工具搞坏代码库是不可原谅的 |
| 分析限时 / 限文件数 | 巨型 monorepo 不该把页面挂死；超限明说 |
| 覆盖率必须随图返回 | 不说明边界的图会被当成完整的真相 |
| 相同输入出相同布局 | 布局跳来跳去没法对比「改动前后的结构」 |
| 路径越界拒绝（复用 SafeJoin 语义） | 与全项目路径护栏同一纪律 |

## 取舍

- **正则而非语法树**：不为一个只读视图引 tree-sitter 级的依赖；
  代价是动态 import 漏解析（用覆盖率兜住，不假装完整）。
- **分层而非力导向**：确定性与可读性；代价是布局美感朴素——架构图要的是
  读得懂，不是炫。
- **不落快照**：又省一张表；代价是没有「结构变迁史」，等真有对比需求再加。

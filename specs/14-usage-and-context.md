# 14 · 用量与上下文水位

## 定位

两件「看得见」的事：这次对话还能聊多久（上下文水位）、
这个月在模型上花了多少（用量统计）。两者都不是给工程师看的诊断信息，
是给办公用户做决策的依据——「要不要开新对话」「这个模型是不是太贵」。

## 上下文水位

### 内核广播

`agent.EventContext` 在**每轮**发模型之前广播一次（在裁剪之后，
所以报的是真正要发出去的数字）：

```go
Event{Kind: EventContext, TokensUsed, TokensWindow, TokensKnown, TokensReserve, Messages}
```

- `TokensUsed` = `EstimateTokens(system, msgs)`，与压缩用的是同一个估算口径
- `TokensWindow` 来自能力目录，可被模型级配置与全局 `context_window` 设置覆写；
  `TokensKnown=false` 表示窗口是估算值，界面读数加「约」前缀（数字照常给）
- 服务层换算成 `ratio`（0-100 整数）再推给前端，前端不必自己算

### 为什么每轮都发

只在「真的裁剪了」时才发是不够的：用户需要的是**水位上涨的过程**，
等它涨满了才知道就晚了。事件很轻（一条整数），不构成负担。

### 展示口径

- 输入框底栏常驻一枚水位环 + 读数（`已用 / 窗口`），0% 也显示——
  什么都不显示等于用户没有这个信息
- 打开 / 切换 / 新建会话时从会话快照（最近一条带 `usage.context` 的助手条目）
  与模型能力回填，不必等下一轮 `chat:context`
- ≥80% 转警告色，≥95% 转危险色
- 窗口为估算值（`known=false`）时读数加「约」前缀，数字照常给，不假装精确

## 用量统计

### 数据来源

`token_usages` 表，每次 LLM 调用一行（`session_id` / `entry_id` / `provider` / `model` /
`input` / `output` / `cached` / `total` / `context` / `latency_ms` / `created_at`）。会话表上另有 `total_tokens`
冗余计数，删除会话时级联清理。

### 接口

`GET /api/v1/stats?days=14`，一次返回全部，前端不拼接口：

| 段 | 用途 |
|---|---|
| `totals` | 总量卡片：输入 / 输出 / 缓存命中量 / 总 token / 调用次数 / 会话数 / 总耗时与平均耗时 / 缓存命中率 / 平均与峰值上下文 |
| `daily` | 每日一柱，长度恒等于 `days`，**没有调用的天补零** |
| `models` | 按模型归因（含 cached），按消耗从多到少，最多 8 个 |
| `sessions` | 用量最高的 5 个会话，供跳转 |

缓存命中量是长对话真正的成本指标（`cached / input`）；平均与峰值上下文
回答「平时一轮有多重、最重的一轮是多少」，是判断「该不该开新会话」的依据。

补零是硬要求：否则 x 轴刻度会随「哪天恰好没说话」而跳动，
用户会以为数据出错了。

### 聚合口径

- `days` 缺省 14，上限 90
- 起点取当天往前 `days-1` 天的本地零点，`localtime` 归组——用户看的是自己的日历
- 平均耗时 = 总耗时 / 调用次数，避免「今天没说话」时均值被拉成 0
- 上下文用量只统计 `context > 0` 的行：没记下上下文占用的调用若计入，会把均值与峰值一起拉低

## 取舍

不做趋势预测、不做预算告警、不做按价格的花费折算。
这些都需要用户额外配置单价与阈值，对本机个人助手是纯负担。
把已经发生的量说清楚，就够用户做「换不换模型」「要不要清一清」的决定了。

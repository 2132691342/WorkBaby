# 14 · 用量与上下文水位

## 定位

两件「看得见」的事：这次对话还能聊多久（上下文水位）、
这个月在模型上花了多少（用量统计）。两者都不是给工程师看的诊断信息，
是给办公用户做决策的依据——「要不要开新对话」「这个模型是不是太贵」。

## 上下文水位

### 内核广播

`agent.EventContext` 在**每轮**发模型之前广播一次（在裁剪之后，
所以报的是真正要发出去的数字）：

```go
Event{Kind: EventContext, TokensUsed, TokensWindow, Messages}
```

- `TokensUsed` = `EstimateTokens(system, msgs)`，与压缩用的是同一个估算口径
- `TokensWindow` 来自 `Config.Budget.Window`，认不出模型名时是 128000 缺省
- 服务层换算成 `ratio`（0-100 整数）再推给前端，前端不必自己算

### 为什么每轮都发

只在「真的裁剪了」时才发是不够的：用户需要的是**水位上涨的过程**，
等它涨满了才知道就晚了。事件很轻（一条整数），不构成负担。

### 展示口径

- 平时低透明度，移进输入框或水位 ≥80% 时才显眼
- ≥80% 转警告色，接近满转危险色
- `window` 认不出来时显示「—」而不是拿缺省值假装准确

## 用量统计

### 数据来源

`token_usages` 表，每次 LLM 调用一行（`provider` / `model` / `input` /
`output` / `total` / `latency_ms` / `created_at`）。会话表上另有 `total_tokens`
冗余计数，删除会话时级联清理。

### 接口

`GET /api/v1/stats?days=14`，一次返回全部，前端不拼接口：

| 段 | 用途 |
|---|---|
| `totals` | 总量卡片：输入 / 输出 / 总 token / 调用次数 / 会话数 / 平均耗时 |
| `daily` | 每日一柱，长度恒等于 `days`，**没有调用的天补零** |
| `models` | 按模型归因，按消耗从多到少，最多 8 个 |
| `sessions` | 用量最高的 5 个会话，供跳转 |

补零是硬要求：否则 x 轴刻度会随「哪天恰好没说话」而跳动，
用户会以为数据出错了。

### 聚合口径

- `days` 缺省 14，上限 90
- 起点取当天往前 `days-1` 天的本地零点，`localtime` 归组——用户看的是自己的日历
- 平均耗时 = 总耗时 / 调用次数，避免「今天没说话」时均值被拉成 0

## 取舍

不做趋势预测、不做预算告警、不做按价格的花费折算。
这些都需要用户额外配置单价与阈值，对本机个人助手是纯负担。
把已经发生的量说清楚，就够用户做「换不换模型」「要不要清一清」的决定了。

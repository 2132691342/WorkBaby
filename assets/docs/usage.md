# 用量与仪表盘

两件事：**这一轮对话还能撑多久**（上下文水位），**这个月在模型上花了多少**（用量统计）。
两者都不是给工程师看的诊断信息，是给办公用户做决策的依据——要不要开新对话、这个模型是不是太贵。

## 上下文水位

### 数据从哪来

水位不再由 WorkBaby 自己算，内核在事件里直接给：

| 来源 | 给什么 |
|---|---|
| `message_update.usage` | 本轮实时 usage（input / output / cacheRead / cacheWrite / totalTokens / cost） |
| `get_session_stats` | 会话累计：token、cost、消息数、上下文占用 |
| `turn_end` | 本轮结束点 |

`tokensBefore` / `tokensAfter` 来自 `compaction_end`，用于「压缩了多少」的展示。

- `context` 是内核报的当前上下文占用；窗口是 `models.json` 里该模型的 `contextWindow`
- 窗口未知（模型未声明）时不给百分比，只给绝对数字并标注「约」
- 给模型输出的余量是 `maxTokens`，与内核的压缩参数 `reserveTokens` 同源

**WorkBaby 不再有本地 token 估算器**。估得再准也是第二份数据源，
和内核真正发出去的数字不一致时，界面会显示「没满」而内核已经开始压缩。

### 为什么每轮都报

只在「真的压缩了」时报不够用：用户需要的是**水位上涨的过程**，
等它满了再知道就晚了。事件很密（一条整数），不构成负担。

### 展示规则

- 输入框底部常驻一个水位环 + 数字（`已用 / 窗口`），0% 也显示——
  什么都不显示等于用户没有这个信息
- 打开 / 切换 / 新建会话时从 `get_session_stats` 回填，不等下一轮的 `chat:context`
- 压缩发生时插一条分隔提示：「已压缩，2.4千 → 2.1千」
- 一轮结束时用 `message_end` 带回来的权威 usage 再校准一次水位：`message_update`
  报的 `context` 是**这一轮开始之前**的占用，不含刚写出去的回复本身，差的那部分在 `done` 时补上
- **环上的百分比是「可用预算」**（`窗口 - 余量`），不是满窗：内核在 `before > 窗口 - 余量`
  时就自动整理，用满窗当比分会慢半拍——整理已经发生、环上还在 87%，用户看着「还有空间」
  却在丢内容。所以 `ratio` 到 100% 的含义是「下一轮就要整理了」

## 用量统计

### 数据从哪来

每次模型调用一行 `token_usages`；按天 / 按模型 / 按会话聚合走 `GET /api/v1/stats`。
聚合口径与对话里逐条显示的用量同源——这一轮 12k，仪表盘也必须说 12k。

### 仪表盘四张卡

| 卡片 | 看什么 | 什么时候该警觉 |
|---|---|---|
| 总 token | 这段时间的累计，以及模型调用次数 | 同样的事调用次数暴涨，说明在多轮反复试 |
| 输入 / 输出 | 你发出去的 / 助手回过来的 | 输入远大于输出，通常是同一个长文件被反复带上 |
| 缓存命中率 | 多少输入 token 走了缓存 | 长期接近 0，说明每次都在全价重发上下文 |
| 平均耗时 | 每次模型调用等了多久 | 突然变长，先看是不是换了更大的模型 |

### 趋势图

按天的 token 曲线，配一张「按模型」与一张「按会话」的分布卡。
看的是形状不是绝对值：哪一天突然高、高在哪个模型、哪个会话。

柱状与环形都用同一组靛蓝色阶（`--wb-ch-1..4`），
颜色只做区分，不编码额外含义——同一个色阶从头到尾，才不会看错。

### 什么时候看一次

- 觉得「这个月好像花得多了」→ 看总 token 与按模型分布
- 觉得「助手变慢了」→ 看平均耗时与某一天的尖峰
- 想找最费 token 的那个对话 → 按会话分布卡，排前面的就是

## 取舍

- **不做预算告警**：阈值是每个人自己的事，替用户定一个「超过 X 就警告」
  只会变成一个被永久忽略的红点。数据摊开，判断留给用户
- **不做成本换算成钱**：不同服务商的计费口径（按 token / 按次 / 订阅）差异太大，
  算出来一个虚假的精度的数字比不算更坏。要看钱，去服务商后台
- **不存第二条用量**：`token_usages` 是唯一一份，仪表盘聚合它、对话逐条显示它
